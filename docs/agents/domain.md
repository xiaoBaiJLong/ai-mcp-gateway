# 领域文档

本仓库采用单上下文（single-context）领域文档结构。

领域文档用于记录项目的核心术语、业务边界和架构决策。项目定义尚未确认时，不应凭空创建业务概念。

## 探索代码前需要阅读

如果下列内容存在，在分析或修改代码前应先阅读：

- 仓库根目录的 `CONTEXT.md`
- `docs/adr/` 中与当前任务相关的架构决策记录

如果这些文件尚不存在，直接继续处理任务，不要将文件缺失视为错误，也不要主动生成没有实际内容的占位文档。

## 目录结构

单上下文仓库采用以下结构：

```text
/
├── CONTEXT.md
├── docs/
│   └── adr/
└── src/
```

其中：

- `CONTEXT.md` 记录领域范围、核心术语及其含义。
- `docs/adr/` 记录重要架构决策及其背景。
- `src/` 存放项目源代码。

## 使用统一的领域术语

在 Issue 标题、规格说明、代码、测试和重构建议中命名领域概念时，应使用 `CONTEXT.md` 中定义的术语。

不要为已经明确定义的概念随意引入同义词。如果需要使用的概念尚未出现在领域文档中，应判断：

- 是否正在创造项目并未使用的词汇；如果是，应重新考虑。
- 是否确实存在领域模型缺口；如果是，应记录并在后续领域建模中补充。

## 处理架构决策冲突

如果计划实施的变更与现有 ADR 冲突，应明确指出冲突，不得静默覆盖已有决策。

说明冲突时，应标明相关 ADR、冲突内容以及重新讨论该决策的原因。
